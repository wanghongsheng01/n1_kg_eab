# Property Graph, Semantic Layer, or Plain SQL? — Replication Package

This package accompanies the ICDE EAB paper *"Property Graph, Semantic Layer, or Plain SQL? An Experimental Study of LLM Question Answering over Multi-Level Product Composition Data"*.

It contains everything needed to rebuild the three benchmark datasets, regenerate every question and gold answer, re-run every substrate with any OpenAI-compatible LLM endpoint, and regenerate all tables, figures and numbers in the paper from the released raw results.

## Layout

| Path | Content |
|---|---|
| `code/build_substrates.py`, `gold.py`, `gen_questions.py`, `check_gold.py`, `semantic.py`, `prompts.py` | The XB synthetic dataset: four substrates (SQL, SQL-U, Graph-T, Graph-U), the metric layer, an independent gold implementation, the question generator and the gold cross-check |
| `code/datasets/aw/`, `code/datasets/lego/` | The same components for AdventureWorks and the LEGO catalog |
| `code/run_pilot.py` | The runner for the single-shot substrates (SQL, SQL-U, Graph-T, Graph-U, Metric, Metric-R, and the pilot variants) |
| `code/run_agent.py` | The runner for the Agent substrate (governed metric tools plus raw SQL) |
| `code/perturb.py` | The perturbed-instance re-check |
| `code/classify_errors.py` | The LLM-assisted error taxonomy |
| `code/analyze_main.py`, `code/make_figs_main.py` | Generate every number, table and figure of the paper |
| `data/*_questions.jsonl`, `data/*_s3_coverage.json` | Questions, gold answers, and metric-layer coverage flags |
| `results/main_*.jsonl` | One record per execution: prompt outcome, generated query or tool trace, result rows, tokens, list-price cost, latency |
| `results/runs*.jsonl` | Pilot runs: repeated runs and the refusal, fallback, registry and agent variants |
| `results/main_*_m2.jsonl` | Metric and Metric-R re-executed after the compiler started rejecting `aggregate: count` without `group_by`; these supersede the Metric and Metric-R records in `main_*.jsonl`, which are kept for transparency |
| `results/main_*_abl.jsonl`, `results/main_*_neo.jsonl` | Ablations (documentation symmetry, optional refusal) and the Neo4j replication |
| `results/tax_main_*.jsonl`, `results/robust_main_xb.jsonl` | Error taxonomy sample and perturbed-instance re-checks |
| `code/build_closure.py`, `code/check_closure.py` | The materialized total-requirements relation (SQL-X `u_explosion`, Graph-X `EXPLODES`), built from the unified databases, and its model-free verification (`results/closure_check.json`, `results/closure_build.json`) |
| `code/metricflow/`, `code/mf_layer.py`, `code/check_mf.py` | The same metric catalog in dbt MetricFlow (dbt projects generated by `gen_projects.py`, built by `build.py`), its compiler wrapper, and the check that reference MetricFlow queries reproduce the gold of every covered question (`results/mf_check.json`) |
| `data/*_questions_para.jsonl`, `code/paraphrase.py` | Paraphrased questions (same ids and gold; `text_orig` keeps the original) and the script that produced and verified them (`results/paraphrase_stats.json`) |
| `results/main_*_g2.jsonl`, `_g2h`, `_neo2` | Graph substrates with the uniform Cypher note (they supersede Graph-T/Graph-U in `main_*.jsonl` and `main_*_neo.jsonl`), the no-sentence (`cypher_nh`, `neo_t_nh`) and separate-note (`cypher_h`) documentation variants |
| `results/main_*_x*.jsonl`, `_mf*`, `_fr*`, `_r1*`, `_para` | SQL-X/Graph-X, MetricFlow, the three further models (`_fr`), the second repetition (`_r1`) and the paraphrased questions |
| `results/tax2_main_*.jsonl` | The second, independent error labeler (same sample as `tax_main_*.jsonl`) |
| `results/main_*_dn.jsonl`, `code/replay_multibranch.py`, `results/replay_multibranch.json` | Review round: the SQL substrates with a DuckDB dialect note (`sql_dn`, `sql_u_dn`, `sql_x_dn`), and the LEGO SQL queries with several recursive branches, which DuckDB rejects, replayed unchanged on SQLite (no model calls) |
| `results/main_*_xtn.jsonl`, `_x_r1`, `_think` | Review round: Graph-X with the usage note on the materialized edge (`cypher_x_tn`), the second repetition of SQL-X and Graph-X, and DeepSeek-Flash with thinking enabled (`ds-flash-think`, 8,000 output tokens) |
| `data/*_questions_fresh.jsonl`, `data/*_s3_coverage_fresh.json`, `results/main_*_fresh.jsonl` | Review round: a fresh question set (seed 20261108, same templates, every instance of the main set excluded, ids prefixed `F`), frozen before it was run, and its runs (SQL, SQL-U, Graph-U, Metric, SQL-X; three main models). Regenerate it with `N1_FRESH=1 python code/gen_questions.py` (and the AW/LEGO generators) |
| `results/retry/`, `results/pre_retry/`, `code/retry_truncated.py`, `code/apply_retries.py` | Truncation rule: runs in which a call stopped at the 1,500-token output cap, re-run once with 8,000 tokens; the originals are kept |
| `results/retry_32k/`, `code/run_v3_think32k.sh` | Thinking runs (`ds-flash-think`) that exhausted their 8,000-token budget, re-run once with 32,000 tokens per call; `analyze_main.py` reports the thinking contrast under both budgets |
| `results/erp_outcomes.csv`, `code/analyze_erp.py` | Enterprise case: one outcome record per execution (template-level question id, class, model, substrate, metric coverage, outcome, route, tokens, cost, latency) and the script that recomputes every enterprise number in the paper |

## Reproducing

Use Python 3.9+ and `pip install -r requirements.txt` (`duckdb==1.4.5`, `kuzu==0.11.3`, matplotlib for the figures). The second graph engine is Neo4j 5.26 Community with JDK 21. All model calls were made between 2026-11-03 and 2026-11-09 through OpenAI-compatible endpoints (`deepseek-flash`, `deepseek-v4-pro`, `kimi-k2.6` from the vendors; `gpt-6-sol`, `claude-opus-5-5`, `Qwen3.8-27B` through a gateway; `glm-4.5-air` in the pilot).

1. **Build the source snapshots.** Run `python code/make_sources.py --raw raw --out data`. It writes `data/{aw,lego,xb}_src.duckdb`, and the result is table-for-table identical to the snapshots used in the paper.
   - XB is produced by a seeded generator.
   - AdventureWorks is built from the CSV exports in `raw/aw/`, which are taken from [microsoft/sql-server-samples](https://github.com/microsoft/sql-server-samples) under the MIT license.
   - LEGO needs the Rebrickable catalog downloads (`*.csv.gz` from rebrickable.com/downloads) in `raw/rebrickable/`. They are not redistributed here. Data sourced from Rebrickable (https://rebrickable.com), whose terms permit any use with attribution; please respect them, including the prohibition on using Rebrickable content to train AI models.
2. **Build the substrates.**
   - XB: `python code/build_substrates.py`.
   - AdventureWorks and LEGO: `python code/datasets/aw/build.py` and `python code/datasets/lego/build.py`.
3. **Regenerate and check the questions.** Run `gen_questions.py` and `check_gold.py` for each dataset. The generators are seeded, so reruns are byte-identical. The gold answers agree with the metric-layer oracle on every covered question.
4. **Run the substrates.**
   ```
   N1_DATASET=aw python code/run_pilot.py --models <m> --substrates sql,sql_u,cypher,cypher_u,semantic,classify --out main_aw.jsonl
   ```
   Set `N1_KEYS_ROOT` to a directory that contains `.secrets/llm_keys.json` with `{provider: {api_key, base_url}}`. `run_agent.py` takes the same arguments. The other substrates are selected with `--substrates`:
   - `cypher_h`: Graph-T with the multi-type pattern note (documentation ablation).
   - `semantic_abs`: Metric with an optional `UNSUPPORTED` answer.
   - `neo_t` and `neo_u`: the two graphs on Neo4j 5.
   - `classify`: Metric-R.
   
   For Neo4j, `code/neo4j_build.py <kuzu_db> <ds>_<t|u> <port_offset>` copies a Kùzu graph into a dedicated local Neo4j instance with identical labels, types and properties. `code/run_neo4j_all.sh` runs the replication; it expects a JDK 21 and a Neo4j 5.26 Community tarball unpacked under `.tools/`.
   - SQL-X and Graph-X: `python code/build_closure.py --ds <xb|aw|lego>` after step 2, then `python code/check_closure.py`.
   - MetricFlow: create a separate environment (`python -m venv .tools/mf_venv; .tools/mf_venv/bin/pip install dbt-metricflow==0.11.0 dbt-duckdb==1.10.0`) and run `.tools/mf_venv/bin/python code/metricflow/build.py`, then `python code/check_mf.py`.
   - `code/run_v3*.sh` are the drivers of the review round (dialect notes, Graph-X usage note, second repetition of SQL-X/Graph-X, thinking contrast, fresh question set, truncation re-runs).
   - `code/run_v2*.sh` are the drivers of the final round (uniform Cypher note, further models, second repetition, SQL-X/Graph-X, MetricFlow, paraphrases). Models served through an OpenAI-compatible gateway (`gpt-6-sol`, `claude-opus-5.5`, `qwen3.8-27b`) read `LLMHUB_BASE_URL` and `LLMHUB_API_KEY` from the environment.
5. **Regenerate the paper's numbers and figures.** Run `python code/analyze_main.py`, which writes `paper/numbers.tex` and the tables, then `python code/make_figs_main.py`. `python code/analyze_erp.py` writes `paper/numbers_erp.tex` for the enterprise case.

## Notes

- Every Kùzu query runs in its own process (`kuzu_exec.py`), because a generated query can crash the engine.
- DuckDB spill space is capped at 300 MB per connection.
- The enterprise case study uses de-identified proprietary data. Its schema, questions, queries and answers are not released; the package contains instead the per-execution outcome records from which every enterprise number in the paper is recomputed. All benchmark conclusions rest on the three public datasets.
